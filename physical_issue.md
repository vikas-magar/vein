# Physical Planner Issues and Completion Tasks

This checklist records the physical-planner issues found during the source audit. The first group contains confirmed defects or gaps that block the example queries. The following groups cover broader unsupported functionality, efficiency, diagnostics, and regression coverage.

## 1. Fix query-blocking planner defects

- [x] **Traverse join-containing aggregate plans during dispatch.** `contains_join` traverses `Aggregate`, and a planner regression asserts aggregate-over-join produces an aggregate transform over a recursive join input. Post-aggregate filter execution remains a separate issue below. DISTINCT over joins is covered by the adjacent completed task. See `crates/physical/src/builder/pipeline.rs:145-164` and `crates/physical/src/planner/default.rs`.
- [x] **Plan DISTINCT over join inputs.** Join detection now traverses `Distinct`; the recursive transform compiler preserves its output projection, and planning lowers it to the existing all-output-columns aggregate over the recursive join result. Planner and runtime regressions verify the physical shape and deduplication of duplicate join rows. Zero-column DISTINCT semantics remain a separate chunk/cardinality issue below. See `crates/physical/src/builder/pipeline.rs:145-220`, `crates/physical/src/compiler/plan.rs:256-300`, and `crates/physical/src/planner/default.rs`.
- [x] **Preserve row cardinality for zero-column DISTINCT.** Zero-column output cardinality is carried by the selection vector and explicitly passed to Arrow record-batch materialization; join gathering and aggregate output preserve row counts without copying column data. Aggregate plans distinguish scalar empty-input groups from DISTINCT, and empty DISTINCT returns no rows. Regressions cover empty/nonempty zero-column DISTINCT, join output cardinality, client materialization, and zero-column record batches. See `crates/exec/src/pipeline/chunk.rs`, `crates/exec/src/operators/aggregate.rs`, `crates/exec/src/operators/join/gather.rs`, and `crates/exec/src/operators/sink/client.rs`.
- [x] **Preserve filters above joined aggregates.** Recursive join planning now compiles filters against the child schema at each transform boundary, including aggregate output schemas, so HAVING predicates execute after aggregation. Planner regression coverage verifies a filter instruction is carried in a transform directly above the aggregate. See `crates/physical/src/compiler/plan.rs:256-267` and `crates/physical/src/planner/default.rs:361-445`.
- [x] **Lower complete join conditions.** The planner extracts one equality as a hash key and compiles remaining `ON` conjuncts into a narrow, vectorized residual predicate carried by `JoinPlan`. The executor evaluates it on hash candidates before tracking matches or generating null-extended rows, preserving outer-join behavior. Planner coverage verifies `NOT LIKE` compilation and build-column mapping; runtime coverage verifies accepted candidates and LEFT JOIN preservation after rejected candidates. Remaining equality conjuncts are evaluated as residuals; extracting all equality keys for composite hashing is covered by the separate multiple-key task below. See `crates/physical/src/builder/pipeline.rs:94-137`, `crates/physical/src/compiler/plan.rs:20-84, 1259-1280`, and `crates/exec/src/operators/join/hash_join.rs:174-249`.
- [x] **Resolve equality join keys by input side, not operand order.** `equality_keys` resolves each column ID against the probe and build schemas, accepting either operand orientation and rejecting same-side or ambiguous keys. Tests cover both orientations and verify selected key positions. See `crates/physical/src/builder/pipeline.rs:314-360, 632-665`.
- [x] **Support multiple equi-join keys.** The planner extracts every cross-input column equality in a compound `ON` condition into paired probe/build key lists and retains other terms as residual predicates. Planner coverage checks key positions and residual preservation; execution coverage verifies every key component must match. See `crates/physical/src/builder/pipeline.rs:94-121, 284-377` and `crates/exec/src/operators/join/hash_table.rs`.
- [x] **Execute post-aggregate operators in recursive join plans.** Recursive input plans now carry Sort and Limit as explicit nodes, preserving their position relative to joins, aggregates, filters, and projections. The executor recursively builds each operator at the correct schema boundary; join plans no longer duplicate root-level sort/limit metadata. Builder/compiler regressions verify node ordering and task metadata, while runtime tests assert ordered results for LIMIT→SORT, SORT→LIMIT, and aggregate→filter→sort→limit combinations. See `crates/common/src/protocol/task.rs`, `crates/physical/src/builder/pipeline.rs`, `crates/physical/src/compiler/plan.rs`, and `crates/exec/src/runtime/mod.rs`.

## 2. Implement required expression and subquery lowering

- [x] **Add vectorized `CASE` and `IN` / `NOT IN` lowering.** The bytecode compiler emits dedicated Micro-IR instructions and the VM executes them with Arrow comparison/zip kernels. `IN` and `NOT IN` preserve SQL NULL behavior, including typed NULL literals; CASE selects the first true WHEN, treats NULL WHEN as false, and emits a typed NULL when ELSE is absent. Parser comma-list syntax requires at least one candidate, so empty lists are not a permitted query form. Compiler, kernel, and VM projection regressions cover NULLs, list negation, empty low-level candidate sets, CASE ordering, and typed NULL output. CASE arms are eagerly evaluated by the current linear VM. See `crates/physical/src/compiler/expr.rs`, `crates/common/src/protocol/ir/op.rs`, and `crates/exec/src/vm/ops/conditional.rs`.
- [x] **Implement correlated `EXISTS` / `NOT EXISTS` for equality-correlated scan filters.** The optimizer extracts one or more direct inner/outer equality keys, retains inner-only filter predicates on the build input, and rewrites the predicate to a left-schema-only semi/anti join. Runtime semi/anti output is existence-preserving after join residual evaluation, emits each probe row at most once, and ignores NULL keys as non-matches. Optimizer and runtime regressions cover `EXISTS`, `NOT EXISTS`, multiple keys, retained inner filters, duplicates, and NULL probe keys. Other subquery shapes, including uncorrelated EXISTS and correlated predicates without direct equality keys, fail with explicit planning errors. See `crates/optimizer/src/rules/exists_decorrelation.rs`, `crates/exec/src/operators/join/rows.rs`, and `crates/exec/src/operators/join/hash_join.rs`.
- [ ] **Extend scalar-subquery support beyond decorrelated aggregates.** The optimizer rewrites supported scalar aggregate comparisons, including correlated equality keys and uncorrelated global aggregates with arithmetic around one aggregate call. General scalar subqueries still have no direct expression lowering, and multi-row scalar cardinality errors are not yet enforced. Expand supported shapes while preserving empty-input and NULL behavior; cover correlated and uncorrelated cases, multi-row results, and decimal coercion. See `crates/optimizer/src/rules/scalar_aggregate_decorrelation.rs` and `crates/physical/src/compiler/expr.rs`.
- [x] **Define join-type support explicitly.** The planner/runtime map Inner, Left, Right, Full, Cross, Semi, and Anti to distinct execution flavors. Cross carries no keys or predicate; Semi/Anti emit only left-side rows, once per left row. Planner and runtime tests cover Cross products and existence joins. Unsupported logical shapes fail during planning rather than being mapped to another join type. See `crates/physical/src/builder/pipeline.rs`, `crates/exec/src/runtime/mod.rs`, and `crates/exec/src/operators/join/rows.rs`.

## 3. Enforce schema and task invariants

- [ ] **Reject unexpected missing join outputs.** When a required logical output column cannot be mapped to either physical input, return a structured planning error instead of silently omitting it and only emitting a debug event. If optimizer pruning intentionally removes a column, make that condition explicit in the plan contract. See `crates/physical/src/builder/pipeline.rs:107-128, 299-330`.
- [ ] **Unify or validate the two task join representations.** A task currently has legacy `build` / `join` fields and the recursive `input_plan`. Define one authoritative representation or validate that incompatible combinations cannot be constructed or dispatched. See `crates/physical/src/task/mod.rs:26-45, 74-103, 149-192`.
- [ ] **Preserve WRITE sink behavior for plans containing joins.** The recursive join builder currently creates a client sink, while the linear builder constructs storage sinks for WRITE. Add recursive WRITE planning with the requested target/options, or return an explicit unsupported-plan error until implemented. Add a test that verifies the sink type and target. See `crates/physical/src/builder/pipeline.rs:49-75, 448-480`.

## 4. Improve efficiency and diagnostics

- [ ] **Avoid cloning the full file list while splitting scans.** `split_file_scan_source` clones the scan, including every path, once per file before replacing the list with a single path. Build each split from shared scan metadata so path copying scales linearly with file count. Add a focused allocation or structural test. See `crates/physical/src/builder/pipeline.rs:406-427`.
- [ ] **Bound temporary register growth.** Review expression compilation so temporary registers can be safely reused between independent expressions where lifetimes do not overlap. The allocator supports watermark release, but compilation currently allocates monotonically. Measure register counts for wide projections and deeply nested expressions before changing behavior. See `crates/physical/src/compiler/allocator.rs:21-63` and `crates/physical/src/compiler/expr.rs:53-109, 251-318`.
- [ ] **Make planning errors concise and actionable.** Avoid embedding the full logical-plan debug tree in common unsupported-node errors. Report the operator kind and relevant child/schema context while retaining detailed structured tracing for debugging. See `crates/physical/src/compiler/plan.rs:409-412`.

## 5. Add coverage and validate behavior

- [ ] **Add planner-level regressions for every fixed issue.** Cover aggregate-over-join dispatch, chained joins, reversed and composite equality keys, residual predicates, outer-join semantics, post-aggregate filters, and output schema invariants.
- [ ] **Add execution-level tests using small fixture data.** Assert rows and schemas, not only that planning returns a task. Include nulls, duplicate keys, unmatched outer rows, and empty inputs.
- [ ] **Add regression coverage for the reported TPCH query shapes.** Keep each query as a named test and assert expected schema and result semantics (using a DuckDB comparison or independently computed expected results where available).
- [ ] **Run the complete project Test configuration and Check configuration after implementation.** Also execute the affected TPCH examples against the local dataset after each relevant feature is implemented.

## Audit notes

- The current `unsupported source node in Parquet pipeline: Join` is first caused by join detection not traversing aggregate wrappers. Fixing that dispatch defect will expose the separate join-condition, expression-lowering, subquery, and post-aggregate gaps above.
- Unsupported logical plan families (for example window, set, pivot/unpivot, sampling, and semantic operators) should either receive deliberate implementations or clear, documented planning errors. The default physical planner currently admits only a subset of logical-plan roots; see `crates/physical/src/planner/default.rs:63-81`.
- The audit was source-based. Each task needs regression coverage and execution-level validation before its behavior can be considered complete.
